# Архитектура платформы: разбор по ТРИЗ

Документ объясняет, ПОЧЕМУ система устроена именно так. Это не описание
кода (оно в комментариях), а разбор противоречий, из которых архитектура
выведена. Правите систему — сначала проверьте, не ломаете ли разрешение
противоречия.

---

## 1. Компонентный анализ

| # | Компонент | Функция |
|---|-----------|---------|
| C1 | Модель курса | Хранит ветки, узлы, треки, синергии, первую неделю |
| C2 | Прогресс ученика | Что освоено, проверки, рефлексия, XP |
| C3 | Идентичность | Кто это и можно ли ему верить |
| C4 | Правила геймификации | XP, уровни, стадии, условия разблокировки |
| C5 | Интерфейс ученика | Сайт, Mini App, личный кабинет |
| C6 | Интерфейс администратора | Правка курса и ведение учеников |
| C7 | Канал связи | Telegram (бот + Mini App) |
| C8 | Хранилище | localStorage на устройстве, KV на сервере |

## 2. Матрица взаимодействий: что работало плохо

Вредные (В) и недостаточные (Н) связи в системе ДО этой работы:

| Связь | Тип | В чём беда |
|-------|-----|-----------|
| C6 → C1 | Н | Модель зашита в `js/data/curriculum.js`. Любая правка курса требует разработчика и деплоя |
| C1 → C2 | **В** | Прогресс ссылается на узлы по `id`. Переименование или удаление узла обнуляет освоенное |
| C2 → C6 | Н | Прогресс лежит в `localStorage` устройства. Администратор не видит ничего |
| C3 → C5 | Н | `initData` существует только ВНУТРИ Telegram. На обычном сайте личности нет |
| C7 → C5 | **В** | Bot-токен нужен для проверки подписи. Попадание его в клиент = компрометация бота |
| C6 → C4 | Н | Правила геймификации — константы в коде |
| C8 → C5 | **В** | Отказ сети не должен убивать обучение, но синхронный клиент именно так себя и вёл |

## 3. Противоречия и их разрешение

### Противоречие 1. Модель должна меняться — и не должна ломать прогресс

> Курс обязан меняться на лету (иначе админка бессмысленна), и курс обязан
> оставаться стабильным (иначе прогресс учеников рассыпается).

**Разрешение — разделение в структуре.** Модель = **база** (версионированный
файл в репозитории) **+ оверлей** (патчи в KV).

- Патч умеет `upsert` и `hide`, но **не умеет `delete`**. Узел исчезает из
  интерфейса, но его `id` продолжает существовать, и прогресс по нему цел.
- Клиент, не получивший оверлей (нет сети, нет бэкенда), показывает базу.
  Это не деградация, а рабочее состояние.

*Приёмы: «местное качество», «предварительное исполнение», «матрёшка».*

### Противоречие 2. Админ должен видеть всех — система должна работать офлайн

**Разрешение — разделение во времени.** Локальное состояние это истина
*момента*, сервер — истина *между устройствами*. Администратор видит
**последний синхронизированный снимок** и рядом — его время. Мы никогда не
показываем снимок как «сейчас»: подпись «данные на такое-то время» это
часть интерфейса, а не сноска.

*Приём: «посредник» (очередь событий), «проскок».*

### Противоречие 3. Нужна регистрация — не нужны пароли и персональные данные

**Разрешение — передать функцию надсистеме.** Личность удостоверяет Telegram.

- Внутри Mini App: подписанная `initData`, проверка HMAC на сервере.
- На сайте: бот выдаёт **одноразовый код** (живёт 10 минут, сгорает при
  первом использовании) → сервер обменивает его на сессионный токен.
- Сервер хранит `user_id`, имя и username. Пароля нет, значит его нельзя
  украсть. Bot-токен живёт только в секретах воркера.

*Приём: «посредник», «выброс и регенерация частей».*

### Противоречие 4. Админка должна быть мощной — и без фреймворка

Правило проекта: только ванильный JS. Ручная форма на каждую сущность —
это сотни строк и гарантированный рассинхрон с моделью.

**Разрешение — дробление + самообслуживание.** Формы **генерируются из
схемы** (`admin/schema.js`). Одна схема описывает поля сущности, один
рендерер строит редактор для любой из них. Добавить поле в узел = дописать
строку в схему, а не править разметку.

*Приёмы: «дробление», «универсальность», «самообслуживание».*

### Противоречие 5. Система должна поглощать новые сущности — и не переписываться

**Разрешение.** Оверлей хранит **типизированные патчи**
(`{entity, op, id, data}`), а не текстовый diff файла. Новый тип сущности —
это новая запись в реестре типов, а не новая ветка кода в пяти местах.

*Приём: «универсальность», «динамичность».*

## 4. Идеальный конечный результат

> Курс меняется **без разработчика**. Ученик меняет трек **без потери
> прогресса**. Администратор видит правду о прогрессе, **не спрашивая
> учеников**. При отказе сервера обучение продолжается.

Каждый пункт ИКР проверяем:

| Утверждение ИКР | Чем проверяется |
|---|---|
| Курс меняется без деплоя | Патч в админке → перезагрузка страницы ученика показывает изменение |
| Прогресс переживает правку курса | Тест `overlay` в `worker/test/run.js`: скрытие узла не трогает `skills` |
| Трек меняется без потерь | Смена трека переписывает только `profile.track` |
| Отказ сервера не ломает обучение | Клиент с недоступным API работает на локальном состоянии, очередь копится |

## 5. Границы честности

- **Снимок ≠ реальное время.** Прогресс попадает к администратору только
  после синхронизации ученика. Интерфейс обязан показывать время снимка.
- **Оверлей не удаляет.** Кнопки «удалить узел» в админке нет и не будет:
  есть «скрыть». Это защита прогресса, а не недоделка.
- **Демо-режим виден.** Без развёрнутого бэкенда кабинеты работают на
  локальном хранилище и честно об этом пишут. Демо-данные не выдаются за
  реальных учеников.
